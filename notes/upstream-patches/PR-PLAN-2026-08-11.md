# KN5000 upstream submission plan — 2026-08-11

Supersedes the "Suggested split into PRs" section of `README.md` for the KN5000 series (PR 6–10).
That split was organised by *what was on the branch*; this one is organised by **what a maintainer
can review in one sitting and see a result from**, which is what Felipe asked for.

Everything here targets **kn5000 only**. KN6000/KN7000 need an MN10300/AM33 core that does not
exist upstream, and KN1500 is gated on a suspected bad IC15 dump; none of the three is submittable
now.

---

## 0. The rules this plan obeys

These are not negotiable and each has cost us something before:

1. **PR branches off `upstream/master` in `~/compartilhado/mame` only.** `kn7000_mame/src` and
   `kn7000-base` are read-only sources to extract *from*. Test merge status by file content —
   rebases hide it.
2. **Anything that is not an honest dump is `NO_DUMP`.** In particular the waveform ROMs: our
   overlay fills IC304/305/306 with `BAD_DUMP` copies of IC307 as a deliberate development
   placeholder so voices play a real-but-wrong timbre instead of silence. Upstream already has
   them correctly as `NO_DUMP` and **must stay that way**. This is the single most likely
   accidental export in the whole series.
3. **Do not export our own regressions.** Two known ones, both absent upstream today:
   - the work-DRAM-persisted-as-NVRAM defect (`map(0x000000,0x0fffff).ram().share("nvram1")`);
     on real hardware only the IC21 SRAM is battery-backed;
   - `kn5000-18`'s SNS write tap, which *caused* the "Sound Name Error" and was removed by
     `kn5000-29`.
4. **No BAD_DUMP as a substitute for a re-dump**, and no re-dump claimed without provenance. See
   PR 1.

### Why the ROM fix leads even though it is the slowest to land

A hash change is the thing maintainers scrutinise hardest, so PR 1 will probably take longer to
merge than PRs 2–5. It still goes first, because every claim about rhythms, styles and the Feature
Demo is downstream of it: without it, MAME's own factory rhythm data is scrambled and any bug
report against the accompaniment engine is chasing a ghost. Submitting sound work on top of a
knowingly-wrong data ROM would be building on sand.

The other PRs do not depend on it and can be submitted in parallel.

## 2. PR 1 in detail — the one Felipe asked for first

**Status: prepared.** Branch `kn5000_ic14_transposed_dump` off `upstream/master` @ `a4f77431604`,
worktree `~/compartilhado/mame-pr-ic14`, commit `40ce9f12b5e` (2-line diff, authored as Felipe).
Full PR description and reviewer notes: **`PR-DRAFT-kn5000-ic14.md`**. Corrected ROM set for
testing: `~/compartilhado/kn5000_corrected_roms/`.

**What upstream has today.** MAME already declares IC14 as a single, flat, unflagged load:

```
ROM_REGION16_LE(0x400000, "rhythm_data", 0)
ROM_LOAD("kn5000_rhythm_data_rom.ic14", 0x000000, 0x400000, CRC(76d11a5e) SHA1(e4b572d3...))
```

That hash is the **scrambled** dump, presented as good. So this is not tidying — it is a
correctness fix to a shipping release.

**What changes.** The hash, and a provenance comment. Nothing else:

```
ROM_LOAD("kn5000_rhythm_data_rom.ic14", 0x000000, 0x400000, CRC(aa4917ce) SHA1(fef7f1927935d8fdada2afbdbfac29aac56e1c3c))
```

**The corrected file** (computed 2026-08-11 from the original dump):

| | size | CRC32 | SHA1 |
|---|---|---|---|
| as dumped | 4,194,304 | `76d11a5e` | `e4b572d318c9fe7ba00e5b44ea783e89da9c68bd` |
| corrected | 4,194,304 | **`aa4917ce`** | **`fef7f1927935d8fdada2afbdbfac29aac56e1c3c`** |

**It is a permutation, not an edit.** Swapping address bits A19 and A21 permutes the eight 512 KiB
blocks by swapping bits 0 and 2 of the block index: `0,1,2,3,4,5,6,7 → 0,4,2,6,1,5,3,7`. Verified
mechanically: the multiset of 512 KiB block hashes is identical before and after, so **no byte was
altered** — only their order, which is exactly what a correctly-wired read would have produced.
The permutation is its own inverse.

**Evidence it is the dumper's rig and not the board** — this is the part that decides whether the
fix belongs in the file or in the driver:

- Service manual page 32 ("CPU SECTION (A) P.C. Diagram") shows IC14 wired **straight**:
  AD20←pin44←net A21, AD19←pin43←net A20, AD18←pin2←net A19, AD17←pin3←net A18, AD16←pin34←net
  A17 — i.e. AD*k* ← net A(*k*+1) throughout, identical to IC19 beside it.
- AD18 and AD20 are pins 2 and 44, adjacent across the NC at pin 1 — the neighbourhood where a
  socket adapter configured for a different 44-pin part mis-maps.

Board-level scrambling is emulated in the driver; a dumping-rig error is fixed in the file. This is
the second.

**Structural verification, content-based and independent of any reference ROM.** Every style
record's lane pointers must land 6 bytes past a cell header `80 FF FF FF FF 87`. As dumped:
**3,439 of 9,696**. Corrected: **9,696 of 9,696**.

**Functional consequence of leaving it wrong.** The bad-opcode watchdog trips, the accompaniment
transport stops, and roughly two thirds of the factory rhythms plus the Feature Demo are silent.

**On `BAD_DUMP`: agreed, it should not be used.** I initially argued for keeping the flag and
de-scrambling in the driver. That was over-cautious and I was wrong: `BAD_DUMP` means the data is
known or suspected to be incorrect or incomplete, and this data is neither — it is the chip's
content, in the chip's order, recovered from a read whose *addressing* was wrong. Marking it
`BAD_DUMP` would misdescribe it.

**The one thing that would make this unarguable.** The corrected file is a reconstruction, not a
second physical read. Felipe owns the instrument, so the strongest possible submission is:
**re-dump IC14 with correct wiring and confirm it produces `aa4917ce`.** That converts the
reconstruction into first-hand provenance, removes every reviewer objection about a hash nobody
has read off silicon, and independently validates the whole analysis. It costs one session.
If the re-dump is not practical soon, submit as above with the derivation stated plainly in the
commit message and let the maintainers decide — but expect to be asked.

⚠ Practical note: MAME ships hashes, not ROM files. A hash change means every user needs the
corrected file, so this should be described in the commit message as a **redump**, with the
derivation and verification in the message body.

## 3. PR 2–7 notes

**PR 2 — data wheel** (`kn5000-25`). Working and verified live: one BPM per detent, direction
correct, holding when the wheel stops. Self-contained, depends only on the already-merged cpanel
device. ⚠ Honest caveat for the PR description: the cpanel HLE *deposits* the encoder scan-table
entry the firmware's main-loop poll (`Encoder_ValueScanAndSync`, ROM 0xFC5761) expects, rather than
emulating the tone-generator encoder register that feeds it. It respects the firmware's idle
discipline, and the code says what it is. A maintainer may ask for the register instead; that is a
fair request and a known follow-up, not a defect.

**PR 3 — floppy.** `kn5000-03` (address map + PORT D bit 6), `kn5000-06` (registers in PC-AT
layout), `kn5000-15` (drive type DD→HD), `kn5000-16` (Timer 0 output → FDC Terminal Count), plus
the dskchg polarity hunk currently riding inside `kn5000-08`. Four mechanical corrections against
the service manual; they belong together as "correct the FDC wiring" and should be four commits in
one PR.

**PR 4/5 — tmp94c241 core.** `kn5000-02` and `kn5000-04`. These touch a shared CPU core, so they
are the ones most likely to get real scrutiny and most likely to help someone else. Submit them
standalone, with the KN5000 symptom quoted as motivation rather than as justification.

**PR 6 — inter-CPU INT0.** ⚠ **Needs re-staging before submission.** Patches `kn5000-26`, `-27`
and `-28` are three historical restoration steps, and the current understanding is
`kn7000_mame` commit `3fd44f3` — *the sub→main wedge is a duplicate INT0 dispatch, not a lost
byte* — which removes the acceptance-time /INT0 re-assertion. That is the patch to submit, written
once, against upstream; do not submit 26–28 as a series, they will read as a narrative of our
debugging rather than a fix. Headline for the description: the MainCPU receive ISR tests its
handshake bits three instructions before reading the latch, the RTOS tick preempts it in that gap,
and the re-asserted /INT0 enters the non-reentrant ISR a second time — the nested dispatch eats the
header and the suspended one parses a payload byte as a header.

**PR 7 — MIDI out** (`kn5000-05`). Tiny, depends on PR 5.

## 3a. The Feature Demo runs before it can be heard

The instrument's built-in Feature Demo is the best single demonstration this driver has: the
machine drives itself through a scripted performance, and whether it gets to the end is a sharp,
self-checking pass/fail that a reviewer can watch. It is worth reaching **before** any audio
lands, and it is reachable — the demo is a sequencer transport plus a display, and it neither
needs nor produces sound to run.

**The chain, as currently understood:**

| needs | why |
|---|---|
| PR 1 — IC14 | with the transposed dump the style engine reads a wrong 512 KiB block, hits an invalid opcode, and the watchdog stops the transport |
| PR 4 — tmp94c241 16-bit timer | the tempo tick |
| PR 6 — INT0 duplicate dispatch | the sub↔main link wedges mid-song without it |
| PR 8a — tone-generator registers | the firmware polls the active-voice bitmap to allocate voices; upstream maps IC303 as `.noprw()`, so that poll returns a constant and voice allocation degenerates |

**PR 8a is therefore the tone generator with the sound taken out**: register decode, voice
allocation state, and the status/keybed reads the firmware polls — no sample fetch, no envelope,
no interpolation, no stream. It is reviewable without any argument about PCM correctness, it is
the piece the demo actually needs, and PR 8b then adds playback on top of a device whose register
semantics have already been agreed.

⚠ **The chain above is inference from our tree, not a measurement.** Our full tree plays 58 % of
the demo; nobody has yet established the *minimal* set on top of upstream. Before promising it in
a PR description, bisect it: start from `upstream/master` + PR 1 and add pieces until the demo
runs to the end. That measurement is cheap and it is what turns "should work" into a claim.

Known open defects that will limit how far it gets, all recorded in
`kn5000-demo-playback-status`: a second stall around t = 131.5 s, and `FindBestSlot` returning
0xFF producing a +85-semitone jump. Neither is a reason to delay 8a; both are reasons not to
oversell it.

## 4. PR 8a/8b/9 — the tone generator

This is the exciting one and also the one most likely to be sent back if submitted whole.
`kn5000-07` is the device plus PCM playback in one commit and should be **split** along the line
in §3a: registers and voice state first (8a), sample generation second (8b). `kn5000-08` … `-13`,
`-21`, `-24` are then six independent refinements (pitch register location, volume/velocity
semantics, stereo pan, waveform selection, pitch scaling, voice hold timer, voice timing with
missing wave ROMs), as one follow-up PR of small commits, or two if review is slow.

⚠ Two things to get right in the description:
- the wave ROMs IC304–306 are **undumped**, and the device must behave sanely without them — that
  is what `kn5000-24` is for. Do not let the placeholder from rule 2 leak in.
- our tree's `kn_tonegen` base class exists to be shared with KN6000/KN7000, which are not
  upstreamable. Extract the KN5000 device without the unused generalisation, or the reviewer will
  reasonably ask what the abstraction is for.
