Six lines, mechanical, restoring what upstream already merged as
`666893f2eb9 cpu/sharc: Fixed off-by-one errors in circular buffer wrapping. (#16016)`:

- `src/devices/cpu/sharc/sharcops.hxx:38` — `PM_REG_I(x) > …` → `>=`

plus upstream's explanatory comment, and the false comment at `build.sh:106-107` in the same
commit ("Only sharc.h/sharc.cpp are overlaid; the rest of the SHARC core is stock" — the next

this for as long as it hid).

**Known consequence:** DSP behaviour moves by one element at the wrap boundary. Any LLE result
calibrated against the old boundary may shift. Upstream's position is that the old boundary was
wrong — the buffer occupies `[B, B+L)`, so an index reaching `B+L` must wrap.

    if '\nwsa1r\n' not in s:

## Step 4 — the prescaler divergence  ✅ settled 2026-09-26

`tmp95c061.cpp:864-867` carries `3/5/7/11`; upstream restored `7/9/11/15` in #16255 after the
user-confirmed ngp/ngpc music regression. The overlay's `tlcs900.h` has no
`execute_clocks_to_cycles()` override, so its counter runs at fc and every TMP95C061 8-bit timer
runs sixteen times fast. This reaches **wsa1/wsa1r**; kn5000 and kn7000 are unaffected.

**Outcome: the overlay keeps `3/5/7/11`, and the reasoning behind it has been rebuilt.**

Felipe asked for the selector decode to be settled. It is, and it turned out not to be the
answer. The databook's own **text layer** carries self-checking worked examples no tap
assumption can reach — *"Given oT1 = 0.32us (at 25MHz), 12.8us / 0.32us = 40"*, *"28.8us /
0.32us = 90 = 5AH"*, and 0.32 us x 25 MHz = 8 exactly — so phiT1 = fc/8, shifts 3/5/7/11. The
decode is equally explicit: *"When T01MOD7, 6 = 00 and T01MOD3, 2 = 01, oT1 becomes the input of
timer 1"*, i.e. selector 01 = phiT1, which is what MAME implements. Upstream's `7/9/11/15` was
never a datasheet reading.

**Three arguments were withdrawn in the process, all of them mine** — see
`FINDINGS-2026-09-26.md`: the circular 488.28 Hz figure, the "INTTR4 never fires" row (upstream
never counts the 16-bit timers at all), and the citation attributing byuu's NESdev post to
"SNK's own NGP developer manual" while drawing the opposite conclusion from what that thread
says. The thread is saved at `ngp-evidence/`.

**Still open, and now correctly framed:** why the NGP behaves 16x off. Not a tap question and
not a decode question — a clock-tree question about a gear SNK's variant has and the TMP95C061
does not, whose documented span (6.144 MHz : 384 kHz) is exactly 16:1. Best candidate, not a
finding. #16255 should stay merged.

Verified after the edit: build 0 errors, `-validate` exit 0, wsa1r boots 96%.
