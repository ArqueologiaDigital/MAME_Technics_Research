# The overlay reverts two merged upstream fixes

Measured 2026-09-26 against `upstream/master` **96016fbe55c**, with the overlay at `ae857fc`
and its base branch `kn7000-base` at `f3c84bef1a7` (**121 commits behind upstream/master**,
5 ahead).

The overlay symlinks its own copy of a file over MAME's, so where upstream has since fixed a
file the overlay also carries, **the overlay build silently gets the pre-fix behaviour**. The
sweep returns **three files**, carrying **two fixes** — #16016 spans two of them. Both fixes are
already merged upstream, one of them ours.

## How this was measured

For every file in the overlay's `src/`, count the upstream commits touching it since the base
branch, then check the fix's own lines against the overlay's copy:

    cd ~/compartilhado/mame
    for f in $(cd ~/compartilhado/kn7000_mame && find src -type f); do
        git cat-file -e upstream/master:$f 2>/dev/null || continue
        n=$(git log --oneline kn7000-base..upstream/master -- $f | wc -l)
        [ "$n" -gt 0 ] && echo "$f  $n"
    done

Three files come back: `sharcdrc.cpp`, `sharcops.hxx` and `tmp95c061.cpp`. Note the sweep must
cover **`.hxx`** as well as `.cpp`/`.h` — an earlier pass of this check globbed only
`*.cpp -o *.h -o *.lay` and missed `sharcops.hxx`, which is where half of #16016 lives.

## 1. tlcs900 prescaler taps — reverts #16255

| | |
|---|---|
| upstream | `b9b23afaf1a cpu/tlcs900/tmp95c061: restore the 8-bit timer prescaler taps (#16255)` |
| overlay | `src/devices/cpu/tlcs900/tmp95c061.cpp:864-867` |

    overlay:    PRESCALE_T1 = 3  T4 = 5   T16 = 7   T256 = 11     // "fc/8" etc.
    upstream:   PRESCALE_T1 = 7  T4 = 9   T16 = 11  T256 = 15

The overlay's `tlcs900.h` has **no** `execute_clocks_to_cycles()` override, so its cycle
counter runs at fc, not fc/2. With taps of 3/5/7/11 against an fc counter, every 8-bit timer
on a TMP95C061 runs **sixteen times too fast** — precisely the regression that garbled ngp
music and that ajrhacker merged the fix for as #16255.

In the overlay this reaches **wsa1 / wsa1r**, which instantiate two TMP95C061s. It does not
reach kn5000 or kn7000, which use the TMP94C241 and the MN10300.

### ⚠ This one is NOT simply a stale revert — the two firmwares disagree

### ⚠ Two arguments withdrawn, 2026-09-26, both of them mine

**The "SX-WSA1R firmware wants 488.28 Hz" argument was CIRCULAR** and must not be cited again.
488.28 Hz is `fc/2048/TREG1` with the databook tap *assumed*; since every Technics firmware sets
TREG1 to fc in MHz, it collapses to 1e6/2048 = 488.28 regardless of the clock. Under upstream's
ladder the same expression collapses just as roundly to 1e6/32768 = 30.52. Measuring 488.2 Hz in
a build that already uses the databook taps is a tautology, not a test. The circular form appears
in `tmp95c061.cpp`'s CORROBORATION paragraph, in `notes/wsa1-probes/README.md`, in
`notes/wsa1-probes/kn1500_timer_regression.lua` ("the same tick from a different crystal") and in
the third NULL bullet of `notes/wsa1-probes/tlcs900_prescaler_scale.py`. Two files quote the figure
soundly and stand as written: `notes/wsa1-probes/wsa1_timer_rate_audit.lua` states the tap from the
databook first and then measures against it, and `notes/audit/kn5000-eg-calibration.md` scores a
TMP94C241 handler identification -- which of the four 8-bit timers drives `INT_HANDLER_14` -- which
its 488.307 Hz measurement can and does discriminate.

**The "INTTR4 never fires under upstream's taps" row was WRONG.** Upstream's `tmp95c061.cpp`
contains **zero** occurrences of `m_timer_change[4` — it never counts the 16-bit timers at all.
That is a missing feature, not a consequence of the tap scale, and it does not belong in a
comparison of tap values.

### What actually holds

The databook settles the taps for the real Toshiba part, in the **text layer**, in self-checking
worked examples that no tap assumption can reach:

    p.81 Table 3.8 (1)      phiT1 = 8/fc, phiT4 = 32/fc, phiT16 = 128/fc, phiT256 = 2048/fc
    "Given oT1 = 0.32us (at 25MHz), 12.8us / 0.32us = 40 ... TREG1 = 40 = 28H"
    "40.64us / 0.32us = 127 = 2n-1 ... 28.8us / 0.32us = 90 = 5AH"

0.32 us x 25 MHz = 8 exactly, and each printed hex value checks out. Shifts 3/5/7/11.

The decode is settled the same way: *"When T01MOD7, 6 = 00 and T01MOD3, 2 = 01, oT1 becomes the
input of timer 1 (8 bit timer mode)"* — selector 01 = phiT1, which is what MAME implements.

The SX-WSA1R conclusion survives, on better evidence than the circular one: the tempo constant
`TREG5 = C/(64 x BPM)` with C = 140,000,000 (`0xFAA378`), the MIDI baud rate of 31250 pinning fc,
and 96 PPQN pinned by MIDI's 24 clocks per quarter, all close on phiT1 = fc/8 without assuming a
tap. `notes/wsa1-probes/tlcs900_prescaler_scale.py` re-derives it and prints `FAILURES: 0`.

| | overlay `3/5/7/11` (= the databook) | upstream `7/9/11/15` |
|---|---|---|
| phiT1 | fc/8 | fc/128 |
| Toshiba databook p.81 | ✓ stated outright | ✗ never a datasheet reading |
| SX-WSA1R tempo / MIDI baud / PPQN | ✓ | ✗ |
| ngp, mic_'s hardware counter | ✗ | ✓ |

**So it is not "which set is stale" and not "both are right".** The databook set is right for the
Toshiba part. Upstream's set is empirically right for the NGP. The NGP is not quite that part.

### Consequence: upstream's own wsa1r runs 16x slow — measured

The corollary nobody had checked. #16204 put the SX-WSA1R in upstream, where it runs on
upstream's taps. Running the overlay's own audit probe against the **upstream** binary
(`~/compartilhado/mame-pr-tlcs900fix/all9-master`, built from `upstream/master` 666893f2eb9):

    t= 44.64  INTT1=  30.52 Hz (n=1364)  INTTR4=   0.00 Hz (n=0)

against 488.2 Hz in this tree. The user-visible cost, on the 900-tick wait at `0xF82804`:

| | INTT1 | 900 ticks take |
|---|---|---|
| this overlay (databook taps) | 488.2 Hz | **1.84 s** |
| upstream (its own taps) | 30.5 Hz | **29.77 s**, measured |

INTTR4 never fires upstream for the separate reason recorded above: it has no
`m_timer_change[4` at all.

So the divergence is not merely cosmetic in one direction. A machine this project contributed
boots sixteen times slower upstream than it does here, and the fix that serves both is a
per-device prescaler base defaulting to upstream's current values, so no existing driver moves
while wsa1/kn1500 select the Toshiba-documented one.

### The NGP: what the 16x probably is

Not a decode error — the databook rules that out above. The live candidate is a feature SNK's
part has and Toshiba's does not.

SNK's variant carries a **BIOS-managed clock gear**; the TMP95C061's complete SFR map (p.174)
has no clock register at all. On NESdev thread 18579, byuu gives its prescaler input as
`6144000/(4, 8, 16, 32, 64)` depending on the gear, and quotes SysPro as saying the input is
"always 384KHz" (which he disputes). The arithmetic is suggestive:

    databook, gear at /4  (what MAME assumes):  phiT4 = fc/32  = 192 kHz
    mic_, measured on real hardware:                            12 kHz
    databook, gear at /64:                      phiT4          =  12 kHz   <-- matches
    SysPro's own gear range 6.144 MHz : 384 kHz              = exactly 16:1

So "the gear is at a setting MAME does not model" reproduces the discrepancy exactly, and the
gear's documented span is exactly the disputed factor. It is the best candidate, **not a
finding** — byuu asserts the opposite, that the NGP runs its gear at the fastest setting.

Note the two NGP authorities disagree with each other, and byuu says so himself: he reports the
databook ratios are what make NGP audio correct in his emulator, while mic_'s hardware counter
gives 12 kHz; byuu's own loop timing misses hardware (0xEA vs 0xFE) and he concludes "the cycle
timings mic_ lists are not accurate". Neither is a settled measurement of a tap.

This is the same factor of 16 left open in the parked `tlcs900-real-timings` branch. It is a
**clock-tree** question, not a tap-value or decode question.

## 2. SHARC circular-buffer wrapping — reverts #16016

| | |
|---|---|
| upstream | `666893f2eb9 cpu/sharc: Fixed off-by-one errors in circular buffer wrapping. (#16016)` |
| overlay | `src/devices/cpu/sharc/sharcdrc.cpp:1795,1801,1816,1822` and `src/devices/cpu/sharc/sharcops.hxx` |

The fix corrects both execution paths. The interpreter half, absent from the overlay:

    -  if (PM_REG_I(x) > PM_REG_B(x)+PM_REG_L(x))
    +  if (PM_REG_I(x) >= PM_REG_B(x)+PM_REG_L(x))
    -  if (DM_REG_I(x) > DM_REG_B(x)+DM_REG_L(x))
    +  if (DM_REG_I(x) >= DM_REG_B(x)+DM_REG_L(x))

and the DRC half, where the overlay still has `COND_LE`/`COND_G` at the four sites upstream
now has `COND_L`/`COND_GE`. The buffer occupies `[B, B+L)`, so an index reaching `B+L` must
wrap; the overlay wraps one element late on both paths.

This matters directly to the KN7000 effects DSP work, which runs on the SHARC.

## Where the base actually stands

"121 commits behind" overstates the content gap. `kn7000-base` forks from upstream at
**6756074d978 = #16204**, so **six of the seven recently merged PRs are already in the base**
(#15878, #15911, #15919, #16190, #16192, #16204). The two that are not are exactly the two
reverted above:

    git merge-base --is-ancestor b9b23afaf1a kn7000-base   # #16255 -> NO
    git merge-base --is-ancestor 666893f2eb9 kn7000-base   # #16016 -> NO

So the base is behind in volume but current in substance, apart from these two — and a rebase
alone will not fix them, because the overlay symlinks its own copies over the rebased tree.

## A third problem, unrelated to the two reverts: wsa1 is not registered

`wsa1.cpp:4342-4343` declares two systems, `wsa1r` and its clone `wsa1`. `build.sh:332` guards
the registration with `if '\nwsa1r\n' not in s:` — and since #16204 merged, upstream's
`mame.lst:27025` already contains `wsa1r`, so the guard is satisfied and the block is skipped
whole. The `wsa1` line is never inserted.

Measured, not inferred: `~/compartilhado/kn7000-emulator/kn7000 -listfull` (binary of
2026-09-22) lists `wsa1r` and **no `wsa1`**. The keyboard variant is compiled and unreachable.
The fix is to split the guard per system, as the kn6000 loop above it already does.

## What is NOT wrong

- **Rebasing the base is free at the git level.** `kn7000-base`'s 5 commits rebase onto
  `upstream/master` with **zero conflicts** (tested in a throwaway worktree,
  `~/compartilhado/mame-rebasetest`, branch `kn7000-base-rebase-test`). Whether the result
  *compiles* is a separate question and is **not measured here** — a second build tree is 28 GB
  and the share is at 96%.
- Every other overlay file that also exists upstream is untouched upstream since the base
  branch, so nothing else is being reverted.
