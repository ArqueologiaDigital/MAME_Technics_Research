# KN5000 I/O census 2026-09-03 — what was landed, and what was not

A pass over the completed disassembly looking for driver gaps: a port the
firmware reads that the driver leaves floating, a register it writes whose
effect the driver ignores, a device it polls that the driver never makes ready,
an interrupt it enables that nothing raises.

Instruments, all committed, all reproducible: `tools/kn5000-io-census/`
(`sfr_census.py`, `rom_bitop_census.py`, `trace_schematic_net.py`, and
`probes/porth_tc_strobe.lua`). Their README says which question each answers
and gives the exact command. Every claim below should be re-derivable from one
of them; where it is not, that is stated.

Sources are the byte-exact trees at `~/compartilhado/kn5000-roms-disasm`
(`v10/maincpu`, `v9/`, `v7/`, `v142/subcpu`, `subcpu/`, `table_data/`,
`hdae5000/`) and the service manual at
`~/compartilhado/technics-docs/service_manual/technics_sx-kn5000.pdf`.

---

## LANDED

### The floppy Terminal Count is main-CPU Port H bit 0 (commit "the floppy Terminal Count is Port H bit 0")

Was: `to0_callback().set(m_fdc, tc_line_w)`. That callback fires on an 8-bit
**timer 0** match. Three independent reasons it can never have worked:

* Timer 0 is never started. `sfr_census.py --only T8RUN v10/maincpu`: the only
  writes are `set 1` (timer 1) at `shared/boot_hw_init.s:73`, and `set/res 3` /
  `res 2` in `boot/system_handlers.s`. No `set 0`, in v10, v9 or v7.
* Port C's timer-output function is disabled — `PCFC = 0x00`,
  `boot_hw_init.s:51`.
* The part has no TO0 pin. IC5 pins 10 and 11 are `PC0/TO1/TO7` and
  `PC1/TO3/TO8`; TO0 does not exist on the package.

Is: `porth_write()` bit 0 → `upd72067::tc_w`. The strobe is
`FDC_Pulse_PH0` (v10 `storage/fdc_routines.s:550`) — `set 0,(PH)` / ~100 nops /
`res 0,(PH)`, i.e. **active high**, and the delay sits only on the high side, as
a strobe should. Its two callers are `INTTC3_HANDLER` (`:2302`), the micro-DMA
channel-3 transfer-end ISR, and `FDC_InitSequence_Full` (`:1326`). Channel 3 is
the floppy's: `FDC_Setup_DMA_Ack_Dest`/`_Src_Ack` (`:600-618`) load DMAS3
(cr 0x0C) and DMAD3 (cr 0x2C) with `0x120000` = `FDC__DMA_ACKNOWLEDGE`
(`fdc_constants.s:17`), `FDC_Setup_DMA_Mode` loads DMAC3 (cr 0x4C) with the byte
count, and `INT5_HANDLER` ("FDCIRQ", `:2314`) writes `DMAR = 0x08` to request it.
`PHCR = 0x09` makes PH.0 an output and `PHFC = 0x1E` leaves bit 0 as plain GPIO,
which is why the pulse is done in software rather than by the pin's own TC0
function (`boot_hw_init.s:61-62`).

Census control: `rom_bitop_census.py --all-bits PH` over the raw v10 and v7
images finds **exactly one `SET 0,(PH)` and one `RES 0,(PH)` in each 2 MB
image** — `FDC_Pulse_PH0` is the only writer of that pin in the machine, so
there is no second call site to change the reading.

Schematic control: `trace_schematic_net.py` on page 32 walks net FDCTC into IC5
pin 145 = `PH0/TC0`. The same run reproduces FDCRST→pin 12 (PD0), FDCINT→pin 13
(PD1/INT4), FDCDRQ→pin 14 (PD2/INT5), FD.H/D→pin 16 (PD5/INT6), FD.I/O→pin 17
(PD6/TI7/INT7) — five bindings the driver already had from an independent
source. A tracer that reproduces five known answers is worth believing on the
sixth.

Behaviour: boots and runs (61.9% and 63.7% over two 40-45 s runs, against 62%
recorded for the previous commit). `probes/porth_tc_strobe.lua` measures
**1 rising and 2 falling** edges over a 45 s boot with no disk in the drive —
the two falls are `boot_hw_init.s:60` and the clearing half of the pulse, so the
strobe executes on the plain boot path and now reaches the FDC. It reached
nothing before. What it does for real floppy I/O is untested: none of the
`.img` files on this machine load into `default_mfm_floppy_formats`.

### Port E's direction comment was describing the pin backwards (same commit as above, comment only)

Not a behaviour change, but it was one edit away from becoming one. Reset
writes `PECR = 0x20` (`boot_hw_init.s:59`, repeated `kn5000_v10_program.s:524`),
which would make PE.5 the port's **only output** — and `tmp94c241::port_r`
returns the latch for output bits, so under that value the `m_cpanel_inta` term
in `porte_read` would be dead code and the driver's "bit 5 (input) = INTA"
comment would be false.

It is not. `CPanel_InitHardware` (`v10 ui/cpanel_routines.s:95-98`) then writes
`PEFC = 0x00` and `PECR = 0x46` — outputs on PE.1/PE.2/PE.6 only, **PE.0 and
PE.5 inputs**. That routine is on the unconditional boot path:
`kn5000_v10_program.s:584` calls through `CPanel_InitDispatchTable[0]` =
`CPanel_InitSequence` (`:2657`), which calls it at `:2662`. The same byte
sequence (`21 00 f0 3b 41 21 46 f0 3a 41`) is present in v7 and v9, where that
file is still largely `.byte` runs — so an absence there is a framing artefact,
not a firmware difference.

**Verdict on PE.5: SETTLED FROM THE ROM, and the earlier fix was right.** The
`m_cpanel_inta` term is live. The trap is that reading only the boot value gives
the opposite answer with equal confidence, which is why the driver now carries
both writes in its comment. Method note worth keeping: a direction register
written twice is a general hazard — `sfr_census.py --only <port>CR` lists every
writer, and the last one on the boot path is the one that counts.

Two corollaries of `PECR = 0x46` / `PEFC = 0x00`, both harmless today:
PE.1's INT9 alternate function is switched **off**, consistent with the
extension IRQ being dead (INTE89 never gets a live priority, the INT9 vector is
`Empty_Handler`); and PE.2, which the driver comments as an input named HDDRDY,
is actually an **output** and the firmware never reads it.

## NOT LANDED, AND WHY

### 1. PD.6 — read as the floppy line AND into the pedal parameter block. UNRESOLVED.

Three readers, and the census is complete (`rom_bitop_census.py --all-bits PD`
finds two `BIT 6,(PD)` in v10 and in v7, matching the source census; the third
uses `LDCF`, a different opcode, so cross-check that one by hand):

| site | routine | what it does |
|---|---|---|
| `storage/fdc_routines.s:2405` | `Reset_Floppy_Disk_Controller` | `bit 6,(PD)` / `ret nz` — PD.6 = 1 skips the whole SPECIFY + seek-sweep sequence |
| `storage/fdc_routines.s:2478` | `Check_for_Floppy_Disk_Change` | PD.6 = 0 → returns L = 1 |
| `audio/audio_control_engine.s:1869` | `MIDI_WriteSecondByte` | `ldcf 6,(PD)` / `scc8 c,c` → a 0/1 value into the parameter block at `0x8EBE`, three instructions after the two Port G pedal reads |

The schematic settles the *pin*: net **FD.I/O** on IC5 pin 17, with a 4.7 kΩ
pull-up (R64) to +5D, i.e. an active-low open-collector line from the drive. It
does **not** settle what FD.I/O means. "Disk change" is a routine *name a
previous pass supplied*, not ground truth, and the two other floppy-side nets on
this sheet (FD.H/D, also pulled up, on INT6) suggest a media-sense pair — a 3.5"
drive gives both `/DSKCHG` and a high-density media sense.

Why this matters and why I did not touch it: the driver reads
`(!floppy->dskchg_r()) << 6`. MAME's `dskchg_r()` already carries hardware
polarity — `m_dskchg = exists() ? 1 : 0` at init, `0` on unload, and it is
restored to 1 by a step with a disk present (`floppy.cpp:563, 737, 1012, 1064`).
So the driver **inverts** it, and with no disk mounted the firmware is told
PD.6 = 1 = "nothing changed", which makes `Reset_Floppy_Disk_Controller` return
before its seek sweep. Removing the inversion would flip boot-time behaviour.
Under the "PD.6 = /DSKCHG" reading the inversion is wrong; under any other
reading of FD.I/O it may be right by accident. **I will not flip a boot path on
a routine name.**

⚠ Do not "resolve" this by picking the reading that makes the emulator behave
better. What settles it:
* the service-manual page carrying the FDD connector (IC208 / the drive header)
  — read the pin names on the cable, not the CPU; or
* **Felipe**: with a disk in the drive and the machine idle, is there a
  behavioural difference between a freshly inserted disk and one that has been
  sitting there (the firmware doing a visible re-seek on insertion)?

The pedal-block read stands open either way: nothing explains why a floppy
status line would be folded into the same parameter array as the foot switches.
Either `0x8EBE` is not a pedal slot, or the two uses are a firmware quirk.

### 2. A device at 0x150000 the driver does not map at all. REAL, but unidentified.

`AudioMix_Init` (`v10 boot/system_handlers.s:1827-1876`), reached
unconditionally from `kn5000_v10_program.s:582` → `Seq_FullInit` → `:1800`,
writes a register-address latch at **0x150000** and register data at
**0x150002**: 4 channels × 8 registers plus four 32-bit combined writes, about
68 stores per boot, every one of them into unmapped space today. Identical in
v9 and in v7 (`:1712, :1728`).

The shape is the twin of what the driver already models on the **sub** bus at
`0x130000`/`0x130002` (address latch at +0, data at +2). `table_data/
boot_cpserial_states.s:931-955` records that this 259-byte library appears three
times — table-data bootloader and maincpu at base 0x150000, sub-CPU boot ROM at
base 0x130000 — byte-identical apart from the three base-address immediates.

Not landed because *which chip answers* is not established, and the tree itself
disagrees with the driver about the sub-bus twin (it calls 0x130000 "the sub
CPU's tone generator"; `kn5000.cpp` calls it DSP1/IC311). Mapping it as a
`.nopw()` stub would hide a real gap behind a fake device; the unmapped-write
log is the honest signal. **This is the strongest candidate for the next pass**:
identify the chip on service-manual p.32 at the IC11 74VHC138 A16-A18 decode
(the driver already has 0x110000 FDC, 0x120000 DMA-ack, 0x130000 ATA on the
card, 0x140000 latch, 0x160000 PPI, 0x170000 VGA — 0x150000 is the hole in an
otherwise regular pattern).

### 3. Main-CPU PD.4 and PA.3 — outputs the firmware barely uses. NOT ACTIONABLE.

* **PD.4** is deliberately made an output (`PDCR = 0x11`, not `0x01`) and then
  never written or read again: `rom_bitop_census.py --all-bits PD` finds **zero**
  `SET/RES/BIT 4,(PD)` in v10, v9 or v7. It sits at 0 forever. The schematic
  explains why nothing uses it — **IC5 pin 15 (PD4) is not connected**; the
  trace finds no wire on that lead at all, while its five neighbours all have
  one. Nothing to model.
* **PA.3** has exactly one `SET` and one `RES` in the whole image
  (0xF97C22 / 0xF97C4B in v10, one each in v7), inside the FDC driver, each
  followed by a *different* delay. That asymmetry is the signature of a real
  strobe, so it is not a misframe — but `PAFC = 0x08` nominally hands PA.3 to
  the DRAM controller, which is hard to reconcile. **Needs the schematic**; I
  did not trace it.

### 4. Main-CPU P7.5 — the constant is right, and it is load-bearing. NO CHANGE.

`port7_read().set_constant(0x20)` is correct and must stay ≥ "ready". Six
readers, all `bit 5,(P7)`, and **four of them are unbounded spins**:
`Flash_IdentifyChip_WaitReady`, `Flash_ProgramWord_WaitReady`,
`TableDataROM_IdentifyChip_WaitReady`, `Flash_ProgramByte_WaitReady`
(`boot/system_handlers.s:6109, 6202, 6654, 6730`), plus `Flash_CheckReady`
(`:6427`) and `HDAE5000_Status_Check` (`:6911`). Polarity: 1 = ready. It is the
flash ROMs' RY//BY line.

⚠ The name `HDAE5000_Status_Check` in the disassembly is a **misnomer** — its
body is byte-identical to `Flash_CheckReady` and it has nothing to do with the
extension board. That name has already leaked into a comment; do not use it to
argue anything about the HD-AE5000. (I cannot fix it: that tree is read-only for
this pass.)

### 5. Main-CPU PE.4 (MICSNS) reads 0 forever. REAL GAP, small.

`CommPort_StatusCheckAndSend` (`audio/note_voice_mapping.s:25993-25997`) is
called from the main loop every pass, samples PE.4, compares it against a shadow
at DRAM `0xE35C`, and on a change sends an 8-byte packet. The driver returns 0
for PE.4, so the compare always matches and that packet is **never sent**.
Not landed because MICSNS is a microphone-sense input with no modelled
microphone, and inventing a value would only make an untested code path run.
A question for Felipe if it ever matters: what does the KN5000 do when a mic is
plugged into the front jack?

### 6. Sub-CPU serial channel 1 is fully driven and can never fire. NOT A DRIVER FIX.

The v1.42 payload programs `SC1MOD = 0x29` (8-bit UART, RXE, BRG clock),
`SC1CR = 0x00`, `BR1CR = 0x0A`, `INTES1 = 0x5D` (INTRX1 and INTTX1 both at
level 5) and primes `SC1BUF = 0xFE`, behind a complete ring-buffer driver with
an RX command protocol (0xF4 = enable RX, 0xF5 = baud change) and a baud table.
Both interrupt vectors have real handlers. Neither can ever be raised: the
driver binds nothing to the sub CPU's SC1, **and** MAME's
`tmp94c241_serial::scNmod_w` logs *"8-bit uart mode (Not implemented yet)"*.
So this needs a CPU-core feature first, and then an endpoint — most likely
CN12, the sub-CPU check terminal whose strap and LED are already modelled, but
nothing in the firmware names it. **Question for Felipe**: is there a serial
diagnostic port on CN12, and what talks to it?

### 7. Sub-CPU NMI is never raised; sub-CPU PE.0 = MUTE is unmodelled. PROPOSAL ONLY.

`MUTE_AND_HALT` (v142 `:290`) drops PE.0 and halts with no `reti`; the reset
value is `PE = 0xFE`, i.e. **mute asserted from reset**, released once by
`AudioLoop_UnmuteAfterBoot` (`:166`) after the tick counter passes 1000. The
driver pulses `INPUT_LINE_NMI` on `m_maincpu` only, and binds no sub
`porte_write`, so neither the mute nor the sub-CPU power-fail path exists in
emulation. Page 33 does show IC27 pin 32 (`/NMI`) connected to a real net
(through a node with C53 0.1 µF to ground) rather than tied to +5D, and there is
a net literally named **MUTE** on that sheet — but I did not finish tracing
either. Not landed because the KN5000 power-down path is load-bearing for the
splash-restore work (`notes/` and the POWER control in the driver), and adding a
second NMI to it on a half-finished trace is exactly the kind of change that
costs a day. Finish the trace first.

### 8. Sub-CPU P6.7 tracks address bit 1 of every tone-generator access. HARMLESS.

365 `set/res 7,(P6)` sites across 183 routines in the v1.42 payload, and in
**365 of 365** the value written equals bit 1 of the address of the very next
tone-generator or keybed access (`0x100000`/`0x110000` → 0, `0x100002`/
`0x110002` → 1). The driver decodes TG-vs-keybed purely by address and does not
wire sub P6 at all, which is correct **only because that invariant holds**. Worth
recording so nobody "fixes" it later. Not landed: nothing to change.

### 9. Small sub-bus map discrepancies. NOT LANDED.

* `0x100004` is read once by the sub **boot ROM** (`AUDIO_HW_WRITE_READ`) and is
  not mapped; the unmapped read returns 0, which is the value the calibration
  loop treats as success — so a probe currently passes for the wrong reason.
* `0x110002` is written once by the boot ROM (`INIT_MEMORY_TEST__no_error`,
  `stiw_da (0x110002), 0x0003`) but the driver maps it read-only.
* `0x1E0000` is mapped `noprw()` on the sub bus with no firmware basis: the
  three occurrences of that constant in the payload are *parameters* to
  `InterCPU_E1_DMA_Transfer`, i.e. destinations in the **main** CPU's SRAM.
* `0x120000-0x12FFFF` is a 64 KB window for a device the firmware only ever
  touches at offset 0.

All four are cosmetic today. Grouped here so a future pass has them.

## Things checked that turned out FINE — recorded so they are not re-checked

* **Port G / the pedals.** Three reads, all in `audio/audio_control_engine.s`
  (`:1844, :1850, :1862`), reached from `Audio_PeriodicUpdate`. The idle test is
  `and a,0xf0 / srl a,4 / cp a,0x0f` → arms a 500-count debounce when the FC
  nibble is all ones, so **0xF is the released state and the pins are active
  low**. The driver's `PEDALS` default of 0xFC is right. Schematic agrees: IC5
  pins 153-158 are PG2..PG7 and pins 151/152 are AN0/AN1 (= EXP and AFT, the two
  analog pedals, which the firmware never reads — ADMOD1/ADMOD2 are written once
  in `MidiParam_ForceResync` and no ADREG is ever read).
  ⚠ Port G is **0x40**. Port Z is **0x68**. A claim naming one and citing the
  other's register number is wrong on its face; that mix-up has already reached
  a docs page.
* **Every interrupt the main firmware enables is raised by something.** Levels:
  INT0 = 1 (raised to 6 inside its own ISR), INT4 = 4, INT5 = 6, INTA = 5,
  INTT1 = 3, INTT3 = 2, INTTR4 = 3, INTRX0/TX0 = 5, INTRX1/TX1 = 5,
  INTTC0/TC2/TC3 = 5. The mismatch runs the other way: the driver raises INT6
  (`fdc hdl`) and INT9 (extension) and the firmware gives neither a live
  priority — both vectors are `Empty_Handler`. Not bugs, just inert.
* **Main-CPU DAREG1** is written by the task scheduler — 0xFF when fully idle
  (`TaskSched_AllIdle`), 0 on dispatch, task priority × 32 when a task is found.
  A CPU-load indicator on a DAC pin, presumably for a scope in the factory. The
  sub CPU does the same. Nothing to model.
* **Main-CPU PF.2** is a plain GPIO driven low at reset and high exactly once,
  in `NMI_ClearGuardAndHalt`, right before `halt` — the "powering down"
  assertion. Nothing consumes it.
* **Main-CPU PH.3** is configured as an output and then never touched:
  `rom_bitop_census.py --all-bits PH` finds zero ops on bit 3 in any image.
* **Ports P0, P1, P4, P5, P6** on the main CPU are never touched at all. Every
  apparent hit is data framed as code.
