# KN6000 / KN6500 — why they showed nothing, and the boot fixes

The KN6000 and KN6500 drivers reuse the KN7000 machine (same MN10300 CPU, same
`screen_update`, same 0x48400000 base), yet booted to a **blank screen**: the CPU
derailed almost immediately and free-ran through unmapped memory. Two stacked root
causes were found and fixed; a third remains.

## Root cause 1 — the firmware dump was only HALF present (FIXED)
The extracted program ROMs had code only in the **low 2 MB**; the upper 2 MB
(0x48600000–0x48800000) was all `0xFF`. But the crt0 ends with `jmp 0x487f7793`,
which landed in that empty region → the CPU executed `0xFF` padding and ran off the
end of the ROM.

Cause: the KN6000/KN6500 firmware update ships as **two floppy `.SLD` parts** whose
decompressed payloads must be **concatenated** (same as the KN7000: `JK1`+`JK2`).
The earlier extraction used only part 1.

- KN6000 (kn6-71.zip → `kn6-v7-1a/b.exe`): `IK1.SLD` (0x200000) + `IK2.SLD` (0x1F7A31) = **0x3F7A31**
- KN6500 (kn65-13.zip → `kn65_v1-3a/b.exe`): `IKV1.SLD` (0x200000) + `IKV2.SLD` (0x181691) = **0x381691**

Reproduce (extraction repo `decompress_sld`, magic `IKPRG4K\0`): decompress both parts,
`raw1+raw2`, pad to 0x400000 with `0xFF`, split ROM_LOAD32_WORD even/odd. With the full
firmware, 0x487f7793 now holds real code (`mov (0x4c3f7894), a3`). Driver ROMs updated;
`verifyroms kn6000/kn6500` = good.

## Root cause 2 — the library is a program-ROM mirror, not self-loaded (FIXED)
The boot-transfer at 0x487f7793 does `mov (0x4c3f7894), sp` — it reads the **initial
stack pointer from the library** at 0x4C000000. Unlike the KN7000 (whose firmware
self-loads its library into libram), the KN6000/KN6500 expect **0x4C000000/0x8C000000
to be a bus mirror of the program ROM**: `*(0x4c3f7894)` = program-ROM `0x487f7894`
= `0x501813c8` (a valid RAM SP); library offset == program offset throughout.

With an empty libram the SP read as 0 → `SP=0xffffffd4` → a RET popped null → derail.
Fix: `machine_start` copies the program ROM into the aliased libram for the KN6xxx
models (`m_lib_mirror`, set by the new `kn6000` machine config). Proven: SP is now
`0x501c6024` (valid) and the boot runs well past the crt0.

## Remaining — a third derail (OPEN)
After the SP is valid the boot still derails to `0x01xxxxxx` (a bad jump/pointer),
so the screen is still blank. Leading suspect: the **table ROM (0x48000000) is also
half-empty** from the same two-part-extraction bug (2nd 1 MB all `0xFF`) — but **no
table `.SLD` was found** among the downloaded CA-Software updates (only program parts
`IK*`/`IKV*` and an `EXTAPR.SLD`). Next steps: (1) tap the low region to find where the
0x01xxxxxx jump originates; (2) locate/assemble the KN6000/KN6500 table image (source
TBD — may need a real-machine dump). Until then both remain `MACHINE_NOT_WORKING`.
