# KN6000 / KN6500 — why they showed nothing, and the boot fixes

The KN6000 and KN6500 drivers reuse the KN7000 machine (same MN10300 CPU, same
`screen_update`, same 0x48400000 base), yet booted to a **blank screen**: the CPU
derailed almost immediately and free-ran through unmapped memory. Two stacked root
causes were found and fixed; a third remains.

## Root cause 1 — the firmware dump was only HALF present (FIXED)
The extracted program ROMs had code only in the **low 2 MB**; the upper 2 MB
(0x48600000–0x48800000) was all `0xFF`. But the crt0 ends with `jmp 0x487f7793`,
which landed in that empty region → the CPU executed `0xFF` padding and ran off the
end of the ROM.

Cause: the KN6000/KN6500 firmware update ships as **two floppy `.SLD` parts** whose
decompressed payloads must be **concatenated** (same as the KN7000: `JK1`+`JK2`).
The earlier extraction used only part 1.

- KN6000 (kn6-71.zip → `kn6-v7-1a/b.exe`): `IK1.SLD` (0x200000) + `IK2.SLD` (0x1F7A31) = **0x3F7A31**
- KN6500 (kn65-13.zip → `kn65_v1-3a/b.exe`): `IKV1.SLD` (0x200000) + `IKV2.SLD` (0x181691) = **0x381691**

Reproduce (extraction repo `decompress_sld`, magic `IKPRG4K\0`): decompress both parts,
`raw1+raw2`, pad to 0x400000 with `0xFF`, split ROM_LOAD32_WORD even/odd. With the full
firmware, 0x487f7793 now holds real code (`mov (0x4c3f7894), a3`). Driver ROMs updated;
`verifyroms kn6000/kn6500` = good.

## Root cause 2 — the library is a program-ROM mirror, not self-loaded (FIXED)
The boot-transfer at 0x487f7793 does `mov (0x4c3f7894), sp` — it reads the **initial
stack pointer from the library** at 0x4C000000. Unlike the KN7000 (whose firmware
self-loads its library into libram), the KN6000/KN6500 expect **0x4C000000/0x8C000000
to be a bus mirror of the program ROM**: `*(0x4c3f7894)` = program-ROM `0x487f7894`
= `0x501813c8` (a valid RAM SP); library offset == program offset throughout.

With an empty libram the SP read as 0 → `SP=0xffffffd4` → a RET popped null → derail.
Fix: `machine_start` copies the program ROM into the aliased libram for the KN6xxx
models (`m_lib_mirror`, set by the new `kn6000` machine config). Proven: SP is now
`0x501c6024` (valid) and the boot runs well past the crt0.

## Remaining — a third derail: uninitialized object/task table (OPEN)
After the SP is valid the boot runs deep (SP moves 0x501813c8 → 0x501c6024) then RETs to
**null** (PC=0, stack top=0). Traced with a fetch-ring: the MILK RTOS scheduler/context
code (library `0x4c03dfxx` == program `0x4843dfxx`; cf. the KN7000 IRQ handler
`0x4C03DDA0`) runs, then the function at **`0x487f6ee0`** RETs to 0. That function loads an
object from a RAM object-table at **`0x50180000`** (`a2 = *(0x50180000 + idx*4)`) — but
boot-stage-2 (`0x487f7383`) initialized that whole 12-entry table to **-1**, so
`a2 = 0xffffffff` (an unpopulated slot); it then writes through the bad pointer and calls
`0x487f4d56`/`0x487f4b66` on it → RET-to-null.

RULED OUT: the **table ROM** (`0x48000000` is NOT read before the derail) and
**`0x84000000`** (already `.ram().share("ram44")`, aliased with `0x44000000`; the KN7000
uses it heavily and works). So the real problem is that **the object/task creation that
should populate `0x50180000[]` hasn't run (or failed)** before this consumer runs —
likely an init-order issue or an earlier bad data-read in the RTOS boot. NEXT: find the
code that writes `0x50180000[]` (the object registrar) and why the slots stay -1; check
whether the scheduler tick fires before object creation completes. Both remain
`MACHINE_NOT_WORKING`.

## Update — the 3rd derail is a TICK-TIMING issue; boot now advances
A write-tap on `0x50180000` confirmed the object registrar **does** run (populates slots 0,1) but is
**preempted mid-loop by the level-6 tick**; the scheduler then runs a task that reads an uncreated slot
(`-1`) → RET-to-null. **Delaying the KN6000/KN6500 tick past the single-threaded boot** (driver
`m_lib_mirror` branch, 2 s) **eliminates the derail** — the CPU no longer crashes; it runs stably and
settles in a **ms-delay loop at `0x4842467d`** (`while ((*0x50276e48) - start <= 6) ;`). Still blank, but
crash → stable is real progress.

**Deeper root — the HLE tick/interrupt model is KN7000-specific.** The delay-loop counter `0x50276e48` is
a **KN6000-only** counter (the KN7000 never writes it). It is init'd to 0 at `0x4847ad7b` by a routine
that programs the **on-chip timers at `0x34001080`–`0x34001092`** (`movhu 0xfa0,(0x34001092)` /
`movbu 0x81,(0x34001082)` / …). So the KN6000 drives its tick from **real timer hardware**, incremented by
its own ISR (write at `0x4847b3ea`) — but the driver models the tick as an **unconditional 1 kHz timer**
vectored to the **hardcoded KN7000 handlers `0x4C03DE26`/`0x4C03DDA0`**, which for the KN6000 firmware are
different code that never touches `0x50276e48`. So the counter stays 0 and the delay loop hangs.

PROPER FIX (future): model the `0x34001080`–`92` timer block and use the KN6000's real interrupt vectors
(or read them from the firmware's vector setup) instead of hardcoding the KN7000's. NEXT: find the KN6000
timer-ISR entry (near the `0x4847b3ea` increment) and the vector the firmware installs for it.

## Update — interrupt-vector trampoline mechanism found; on-chip timers are the remaining blocker
KEY: the AM33 interrupt vector is a **firmware-built trampoline table at `0x90000000`** (`cb dc <disp32>` =
`nop; jmp`, with disp = target − 0x50000001 so it jumps to target+0x40000000 via the 0x8C alias). The
KN7000 builds slot0 `0x90000000` → `0x4C03DE26` (scheduler / lvl 6) and slot1 `0x90000006` → `0x4C03DDA0`
(quick dispatch); it installs the scheduler slot at `0x48410080`. The driver had **hardcoded those KN7000
targets**. **Fix (committed): for the KN6xxx, vector interrupts to the trampoline (`0x90000000`/`0x90000006`)
instead of the hardcoded target**, so each firmware's own handler runs. Verified: the KN6000 tick now
executes its trampoline (`TRAMPOLINE EXEC @0x90000000`); the KN7000 still boots to its screen (nonblack≈4594;
change gated on `m_lib_mirror`).

REMAINING BLOCKER (now precisely scoped): the delay-loop counter `0x50276e48` still does not advance — it
is incremented by a **separate on-chip timer ISR** (increment at `0x4847b3ea`), NOT the driver's level-6
tick. The boot's timer-setup at `0x4847ad60` programs **two on-chip timers**: `movhu 0x7d0,(0x34001090)` +
`movbu 0x81,(0x34001080)` and `movhu 0xfa0,(0x34001092)` + `movbu 0x81,(0x34001082)`. The driver does not
model this timer block (it only has the KN7000's HLE unconditional 1 kHz tick on its own INTC group). NEXT:
model the `0x34001080`–`92` timers (capture control/reload, run a MAME timer per enabled timer, assert its
INTC group on expiry) so the counter advances and the boot proceeds past the delay loop. The trampoline
vectoring is already in place to route the resulting interrupt to the KN6000's own ISR.

## Update — timer counters (first cut); boot reaches a timer self-test halt
Confirmed the KN6000 boot is gated on the on-chip timers. A no-rebuild HLE test (lua drives the software
ms-counter `0x50276e48`; a new driver handler advances the hardware counter `0x340010a2`) lets the boot
progress through BOTH timer busy-wait loops:
- `0x4842467d`: waits on the software counter `0x50276e48` (incremented by the timer ISR `0x4847b3e0`).
- `0x4847b21c`: waits on the hardware timer counter `0x340010a2` (until it advances by `0x1b58`).

…then it reaches **`0x4847b238` = `bra 0x4847b238`** (a deliberate self-loop HALT), right after
`bset 0x08,(0x36008004)`. The poll loop has no early-exit, so this is a timer-timing self-test / error path:
the crude HLE (counter at a placeholder rate, no real timer interrupt) drives the boot into it.

Driver change (committed): `map(0x340010a0, 0x340010af)` for the KN6xxx returns a down-counting value
(`-(total_cycles>>4)`) so the hardware-counter poll loops advance — correct-in-principle (the register
should count, not read 0), gated on `m_lib_mirror` (KN7000 unaffected, still boots nonblack≈4594). The RATE
is a placeholder, and the software counter still needs the real timer **interrupt** (the ISR increments
`0x50276e48` + does the tick work). NEXT: build the proper timer model — decode the timer mode
(`0x34001082`=0x81) for the clock/rate, run a MAME timer per enabled timer, assert its INTC group on expiry
(group TBD), and match the counter-register rate — so the self-test passes instead of halting.

## Update — the on-chip ms-timer is INTC group 7; boot clears both delay loops (halt is next)
Found (GxICR write-tap): only groups **6** (`0x34000118`, level 6) and **7** (`0x3400011c`, level 4) are
enabled at boot. Group 6 = the scheduler tick (fires; ISR at `0x4c171c1f`). **Group 7 (level 4) = the
on-chip ms-timer** — never asserted by the old driver. Fix (committed): the KN6xxx tick also
`intc_assert(0x07)`, so the REAL ms-timer ISR now increments the software counter `0x50276e48` (no HLE).
Result: the boot clears BOTH delay loops (`0x4842467d` via group 7; `0x4847b21c` via the hw-counter handler)
and reaches `0x4847b238` by t=2. KN7000 unaffected (gated; boots nonblack≈4594).

The `bra 0x4847b238` hard self-loop halt is **not** an HLE artifact (reached with the real timer too). It
sits in a routine at ~`0x4847b1a0` that **disables interrupts** (calls `0x4847b000`, which clears the ENABLE
bit in GxICR groups 29/30 at `0x34000174`/`78`), toggles the `0x36008004` chip-select GPIO, writes LCD reg
`0x9000000e`, runs the timer-delay, then hard-halts. That profile = a **fatal-error / shutdown / reset
path** — the boot deliberately halts after timer init. NEXT: find the CALLER of ~`0x4847b1a0` (the
decision/check that routes here) to learn what the boot is failing (likely an unmodeled peripheral or a
self-test the emulation doesn't satisfy).

## Update — the halt is a scheduled RTOS TASK (the RTOS is up)
Traced the path to `0x4847b238`: the scheduler (dispatch `0x487f72aa` → context-restore `0x487f7a07`, which
loads the current TCB `*(0x5018002c)`, restores its stack + registers, and `rti`s to the task's saved PC)
resumes a TASK whose PC is `0x4847b19c` — the shutdown/halt routine. So the RTOS is up and multitasking;
the *current task* is running the disable-interrupts + chip-select + LCD + delay + hard-halt sequence. This
is either the idle/shutdown task (⇒ the main boot task is blocked or finished) or an error task. NEXT:
trace the task's ENTRY into `0x4847b1xx` (before the preemption) to learn whether the main boot task
blocked/errored and the scheduler fell back here — i.e., what event the main task is waiting on.
